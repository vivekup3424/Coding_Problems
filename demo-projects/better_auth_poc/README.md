# Better Auth PoC

Minimal TypeScript/Node.js proof of concept for [Better Auth](https://www.better-auth.com/),
using Express + SQLite (via `better-sqlite3`) and email/password authentication.

## Structure

- `src/auth.ts` — Better Auth instance config (database, secret, email/password provider).
- `src/server.ts` — Express server. Mounts Better Auth's handler at `/api/auth/*` via
  `toNodeHandler`, and shows a custom protected route (`/api/me`) that reads the session
  with `auth.api.getSession()`.
- `public/index.html` — plain HTML/JS page (no client SDK/bundler) that calls the auth
  REST endpoints directly with `fetch`, to make the wire protocol visible.
- `better-auth_migrations/` — SQL migration generated by the Better Auth CLI for the
  `user`, `session`, `account`, `verification` tables.
- `sqlite.db` — local SQLite database (gitignored).

## Run it

```bash
npm run dev
```

Then open http://localhost:3000 and try Sign up → Check session → Sign out.

If you change the auth config (e.g. add a plugin with new fields), regenerate/apply
schema with:

```bash
npx @better-auth/cli generate --config src/auth.ts -y
npx @better-auth/cli migrate --config src/auth.ts -y
```

## What was verified (via curl)

- `POST /api/auth/sign-up/email` creates a user + session, returns a session token and
  sets a session cookie.
- `POST /api/auth/sign-in/email` with correct credentials authenticates; wrong password
  returns `401 INVALID_EMAIL_OR_PASSWORD`.
- `GET /api/auth/get-session` and the custom `/api/me` route both correctly read the
  session from the cookie; both return `401` with no cookie.
- `POST /api/auth/sign-out` invalidates the session — **but only succeeds if an `Origin`
  header is present**. Better Auth enforces origin checking on state-changing requests
  once a session cookie is in play (CSRF protection) — real browsers send `Origin`
  automatically, curl does not. This only surfaced on sign-out here because sign-up/
  sign-in don't yet have a session cookie to protect.

## Key takeaways

- Better Auth owns its own DB tables and migrations — you point it at a driver
  (`better-sqlite3`, `pg`, etc.) or an ORM adapter (Drizzle/Prisma/Kysely), not the other
  way around.
- The core is framework-agnostic: it exposes a web-standard `Request -> Response`
  handler (`auth.handler`), and `better-auth/node`'s `toNodeHandler` adapts that to
  Express/Node's `req`/`res`.
- Session validation elsewhere in your app is just `auth.api.getSession({ headers })` —
  no separate middleware/session store needed, since it reads the same cookie.
- CSRF protection is on by default and tied to `trustedOrigins` — worth remembering
  when a frontend origin differs from the API's `baseURL`.
